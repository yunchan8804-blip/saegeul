# Gemma 성능 계측과 띄어쓰기 제안 후속 작업

> 최신 상태: 종결부호 누락 재현 후 프롬프트·거부 사유 계측·미충전 자동 준비·첫 기능 안내를 수정했다. 추가 요청으로 MODERATE에서는 소량 준비하고 SEVERE부터 중지하도록 변경했다. 최종 통합 단위 테스트는 1,160개 중 1,153개 통과, 기존 스킵 7개다. 직전 설치 앱에서 공개 20/20문맥 보존과 실제 터치 삽입을 확인했다. 새 발열 정책의 실기기 검증과 전체 새 문장 품질 평가는 아직 진행 중이다. 아래 초기 기록은 당시 상태로 보존하며, 이번 작업은 마지막의 품질 후속 절에서 추적한다.

## 범위와 완료 기준

기준은 `ca0240b1`, 브랜치는 `YunChan/gemma-ondevice-materials`다. [핸드오프](HANDOFF-gemma-material-performance-2026-09-09.md)의 미완료 게이트를 추적한다. 모델은 기존 Gemma 4 E2B, LiteRT-LM 0.13.1, CPU, 기본 sampler, 2048 token 상한을 유지한다. 새 모델 다운로드, 정식 앱 승격, 버전 변경, 커밋·push는 포함하지 않는다.

입력 중 추론하지 않는 제품 경계는 [한국어 스마트 입력 SSOT](korean-smart-input-ssot.md)를 따른다. 공개 20문맥 보존, 3문맥 표시 1초 및 정확한 touch 삽입, 취소·중지, 한국어 자연스러움은 각각 독립 게이트다. 일부 테스트 통과를 임의 문장 생성·교정의 완벽함으로 해석하지 않는다.

## 구현과 측정 계약

- `GemmaGenerationMetrics`는 해시 검증, 엔진 초기화, conversation 생성, 추론, native 종료, 전체 실행 시간을 분리한다. 실패·취소된 단계도 소요 시간을 남기고 기존 예외와 cleanup 실패를 보존한다.
- RAM은 250ms 주기 PSS 관측의 최대값과 가용 메모리 최저값이다. 실제 순간 최대값은 아니다. 열 상태 시작·종료와 MODERATE 최초 관측 시간을 함께 기록한다.
- `GemmaMaterialPerformanceDeviceTest`는 충전·배터리·열·메모리·키보드 guard를 유지하고 은행 저장·재로드 비용과 추가·중복·거부 수를 기록한다. 새 요청 시작 예산은 120초다.
- 생성량은 2개와 1개, 호출 간격은 0초와 10초를 한 번에 한 변수씩 비교한다. 기존 은행의 고유 추가 수는 이전 실행과 중복 축적에 영향을 받으므로 `existing_bank_order_dependent`로 표시한다. 추가가 0이면 재료당 비용은 0이 아니라 null이다.
- 기본 계측에는 원문이 없다. `reviewFreshPublicResponse=true`일 때만 이번 공개 고정 프롬프트의 새 생성 응답을 PII 검사 후 별도 품질 검토에 제공한다. 은행에서 읽은 문장 본문이나 개인 입력을 출력하지 않는다. JSON 파싱 실패·PII 거부는 본문 없이 기록한다.
- 띄어쓰기 제안은 저장된 문장과 공백을 제외한 글자·부호가 같은 완결 문장에만 적용한다. 모호한 저장 후보, 다른 글자·종결부호, PII, 비ASCII 공백은 거부한다. 메모리 인덱스를 사용하며 모델을 호출하지 않는다.
- 후보 선택 시 세션·커서·선택 영역·원문을 재확인하고 정확히 한 번 교체한다. 실패 시 다른 삽입 경로로 우회하지 않는다. 생성 재료를 개인 작성 문장으로 학습하지 않는다.

## 검증 기록

통합 빌드 `integrated-r2`는 JDK 17에서 1분 11초에 성공했다. XML 직접 집계는 1,143개 중 통과 1,136개, 기존 스킵 7개, 실패·오류 0개다. 첫 실행은 sandbox 밖 Gradle 캐시 잠금 파일 접근 거부로 빌드 시작 전에 실패했고 캐시 접근 권한을 요청한 재실행에서 성공했다.

중간 앱 APK SHA-256은 `3C207D89599306950B9CA63B2DDDAC1D524DC2735506570F6D788EEFADE05CD9`다. AndroidTest는 후속 테스트 변경 때문에 재빌드가 필요하며 최종 검증 해시와 구분한다.

첫 성능 실행은 열 상태 상승으로 SHA-256 검증 중 취소됐다. 검증 워커가 명령 실행 시 전체 로그를 저장하지 않아 사후 재구성한 `performance-baseline-r1.log`는 **원문 성능 증거로 수용하지 않는다**. 부분 보고 수치는 최종 비교표에 사용하지 않는다. 기존 은행과 자동 축적 꺼짐 상태는 보존했다. 이후 명령은 실행 시 전체 출력과 프로세스 종료 코드를 직접 파일에 기록한다.

실제 `ondevice_generated` 후보 표시·터치는 `latency-r1`에서 3문맥 모두 통과했다. JSON 원문을 직접 읽은 표시 시간은 `회의 자료를 ` 429ms, `오늘 저녁 ` 371ms, `약속을 ` 343ms다. 각 `clickInsertionMatched=true`를 확인했다. 이는 모델 추론 시간이 아니라 메모리 재료의 화면 표시 시간이며 전체 터치 완료 시간과 구분한다.

띄어쓰기 `replacement-r1`은 6개 중 3개 통과·3개 실패다. 직접 교체와 재클릭 차단, 오래된 세션 차단, commit 거절 보존은 통과했다. 두 테스트는 debug 화면의 접근성 설명 불일치로 실행 경로에 진입하지 못했고, 저장 재료의 실제 touch는 교체 결과가 일치하지 않았다. 실패를 원인별로 수정·재검증하기 전에는 띄어쓰기 기능을 완료로 표시하지 않는다.

후속 `replacement-r4`는 **6개 모두 통과**했다. 전화번호 칸은 교체 함수의 대화형 필드 검사로 차단하고, touch 테스트는 실제 layout과 접근성 좌표가 일치할 때까지 기다린 뒤 실행했다. 초기 editor 준비 검사 결과를 버리던 테스트 helper도 수정했다. 직접 교체·재클릭 차단·동일 길이 원문 변경·이전 세션·입력 거절 보존·실제 저장 Gemma 재료의 UI 터치가 포함된다. 진단값 `A11yLiveBoundsMatch`, `AfterMatchesTarget`, `Injected`, `UiIdentityCursorMatchesSelection`은 모두 true다.

최종 앱에서 `latency-r2`도 통과했다. `회의 자료를 ` 426ms, `오늘 저녁 ` 393ms, `약속을 ` 336ms에 표시되고 세 문맥 모두 실제 touch 결과가 일치했다. 마지막 전체 단위 테스트는 1,143개 중 통과 1,136개, 스킵 7개, 실패·오류 0개다.

검증 앱 SHA-256: `88667EC8AA611867D95F6B54323DD12CA2CA315AAB7DCEC8C79B8FFED4AC6763`. 위 UI 검증 AndroidTest SHA-256: `FE828ACB720374EAFEA4DCB999CA64A258347585A3DB1052BA7CB5E6A79B4C44`. 이후 coverage 전용 검사 추가 APK와 구분한다.

현재 **실기기 생성 조건 비교·20문맥 coverage·전체 자연스러움은 미완료**다. 띄어쓰기 제안과 지정 3문맥 touch 성공으로 이 상태를 대체하지 않는다. 생성량 1개/2개와 간격 0초/10초의 비교 시작 전에 MODERATE가 반복 관측되어 조건을 완화하지 않고 중단했다.

## 공식 근거와 판단

[Gemma 4 모델 카드](https://ai.google.dev/gemma/docs/core/model_card_4)는 E2B의 온디바이스 용도와 다국어 능력을 설명하지만 한국어 키보드 교정의 완벽함을 보장하지 않는다. 작은 모델로의 교체는 한국어 품질과 대상 Android artifact 호환성 증거를 확보하기 전에는 채택하지 않는다.

[Android Thermal API 안내](https://developer.android.com/games/optimize/adpf/thermal)는 열 제한에 접근할 때 작업량을 줄이고 열을 방출할 여유를 두도록 설명한다. 기존 MODERATE 중지 경계를 유지하며, 열 상태 하나로 앱 시작이나 금고 진입 지연의 원인을 단정하지 않는다. 모델 상주 재사용이나 해시 검증 생략은 채택하지 않았다.

로컬 원문은 `.artifacts/gemma-performance-20260909/`에 보존한다. 모델·APK·로그·캡처는 커밋하지 않는다.

## 현재 중단 지점과 재개 순서

`coverage-readonly-r1`의 실제 관측은 전체 은행 28개, 공개 문맥 11/20이다. 두 번 재로드한 문맥별 개수는 같고 생성은 실행되지 않았지만, 9문맥이 비어 있어 테스트는 실패했다. 비어 있는 문맥은 `자료를 확인하고 `, `답장이 늦어서 `, `시간이 괜찮으면 `, `일정이 바뀌면 `, `비가 많이 와서 `, `조금 늦을 것 `, `잘 이해가 안 돼서 `, `다음에 기회가 되면 `, `확인해 주셔서 `다.

마지막 `state-after-coverage-r1.log`는 thermal MODERATE(2), 자동 축적 `enabled=false`다. 모델과 은행을 삭제하지 않았다. 최종 설치 AndroidTest SHA-256은 `80ECD93C8BB672EF62360ADF0172897650F3900004FCF816346FFA245E0492DE`이며, 앞의 UI 통과 APK에 coverage 검사 메서드만 추가한 빌드다.

1. `adb devices -l`로 현재 Fold6 연결을 다시 확인한다. 충전·배터리·메모리·키보드 guard와 thermal MODERATE 미만이 실제로 충족돼야 생성한다. 열 상태가 유지되면 같은 추론을 반복 실행하지 않는다.
2. `GemmaMaterialPerformanceDeviceTest#measurePublicMaterialGenerationOnDevice`를 `maxRequests=2`, `prefixStart=0`, `reviewFreshPublicResponse=true`로 실행한다. 남은 조건은 `sentenceCount=1, intervalMs=0`과 `sentenceCount=2, intervalMs=10000`이다. 기존 baseline은 2개/0초다. 명령 출력을 실행 시 `Tee-Object`로 저장하고 `$LASTEXITCODE`와 instrumentation 내부 성공/실패를 구분한다.
3. 위 부족 문맥을 기존 자동 축적 정책 안에서 채우고 공개 생성 원문 품질을 검토한다. 시도 횟수를 몰래 초기화하거나 후보를 하드코딩하지 않는다. 부족 문맥 번호는 4, 5, 8, 11, 14, 16, 17, 18, 19다.
4. 20문맥 coverage·재로드를 다시 확인한 뒤 기존 `GemmaAccumulationDeviceTest`, `GemmaAccumulationKeyboardDeviceTest`로 새 계측 코드의 자동 축적 끄기·키보드 중지·저장 보존을 검증한다. 이번 후속 작업에서 이 두 생성 기반 테스트는 재실행하지 못했다.
5. 최종 앱이 바뀌면 3문맥 source/touch와 띄어쓰기 6검사를 재검증한다. 문장 제안은 입력 중 추론 시간이 아니라 표시 시간을 비교한다.

오케스트레이터가 탐색·공식 조사 결과를 평가하고, 계측·띄어쓰기 인덱스·UI 연결을 워커에게 나눠 맡겼다. 계측의 실패 시간/경쟁 조건과 UI 검증 실패는 재작업 후 수용했다. 첫 성능 로그의 사후 재구성은 증거로 반려했고 이후 실행 시 원문 수집으로 전환했다. 전체 목표는 아직 완료되지 않았으며, 저장된 재료의 띄어쓰기 제안은 임의 문장의 조사·어미·의미까지 고치는 범용 교정기가 아니다.

### 두 번째 goal 턴 재확인

`continuation2-state.log`에서 Fold6 연결·충전·배터리 100%·자동 축적 꺼짐을 확인했다. ADB thermal은 LIGHT(1)였으나 `performance-count1-r1`의 실제 요청 시작 검사에서는 MODERATE(2)여서 **모델을 실행하기 전에 실패**했다. 내부 결과 Tests 1 / Failures 1, ADB exit 0이며 `interval10`은 실행하지 않았다. 따라서 이 실행은 1문장 생성 성능 표본이 아니다. 외부 조회가 잠깐 LIGHT였다는 이유로 앱 내부 guard를 건너뛰지 않는다. 이 관측은 이번 열 상태 상승을 모델 추론만의 결과라고 단정할 수 없다는 근거이기도 하다.

### 세 번째 goal 턴: 외부 상태 차단 확정

`continuation3-state.log` 원문에서 Fold6 `100.109.125.97:39155` 연결, thermal MODERATE(2), AC 충전, 배터리 100%, 배터리 온도 39.2°C, 자동 축적 `enabled=false`를 확인했다. 조회 exit은 0이다. 시작 조건이 충족되지 않아 모델과 성능 테스트를 호출하지 않았다. 모델·은행·설정은 그대로 보존했다.

같은 실제 열 차단이 최초 작업 턴과 두 차례 자동 연속 턴에서 반복됐다. 남은 생성 비교·20문맥 보충·생성 중지 검증을 진행하려면 실제 열 상태 변화가 필요하므로 목표를 `blocked`로 기록한다. 이는 완료 판정이 아니다. 기기가 식은 뒤 위 재개 순서대로 내부 guard까지 재확인하고 계속한다.

### 자동 축적 후 최종 관측

`coverage-accumulation-cooled-r1`은 기존 scheduler/attempt 정책으로 10회 실행 후 380.721초에 18/20문맥 미충족으로 실패했다. 중간 thermal 0→1→2 및 냉각 대기가 관측됐다. 누적 added 30·rejected 24·duplicates 38은 이번 실행 증가량과 구분한다. 종료 후 자동 축적 false, thermal 2를 확인했다.

생성 없는 `coverage-after-accumulation-cooled-r1`에서 전체 은행 43개, 18/20문맥, `reloaded=true`, `generationActive=false`를 확인했다. 빈 문맥은 인덱스 8과 18이다. 워커의 최초 보고 3개는 원문상 2개와 달라 반려·정정했다. 재로드 보존은 통과했지만 20문맥 gate는 내부 1 test/1 failure로 여전히 실패다.

다음에는 두 빈 문맥의 새 공개 생성 응답과 거부 사유를 확인해야 한다. 과거 공개 비교 문서에는 두 FULL 출력의 종결부호 누락이 있으나 이번 실패 원인으로 단정하지 않는다. 시도 횟수 초기화나 저장 검증 완화로 coverage를 채우지 않는다. 전체 자연스러움과 범용 문법·의미 교정 품질 증거는 여전히 부족하다.

## 품질 후속과 충전 조건 개선

이번 원문은 `.artifacts/gemma-quality-followup-20260909/`에 보존한다. 기존 빌드에서 빈 문맥 8과 18을 각각 한 번 생성한 `missing-prefix8-before-r1.log`, `missing-prefix18-before-r1.log`는 모두 내부 `OK (1 test)`였으나 신규 0개·거부 2개다. 공개 응답 4개 모두 종결부호가 빠져 있었다. 이는 계측 실행 성공이며 저장 품질 통과가 아니다.

생성 프롬프트는 전체 문장 3~12어절, 정확한 앞부분과 마지막 공백, 요청 개수, 종결부호를 명시하도록 변경했다. 첫 수정의 새 응답에는 질문의 느낌표 종결과 시점이 어색한 표현이 있어 수용률만으로 품질을 판정하지 않았다. 두 번째 수정은 친구·동료에게 보낼 자연스러운 존댓말과 앞부분의 뜻·시점, 질문의 `?`·평서의 `.`를 요청한다. 개수는 공용 API 인자로 받으며 성능 테스트의 문자열 치환을 제거했다. 저장 규칙은 완화하지 않았고 임의로 부호를 붙이지 않는다. 거부는 원문 없는 사유별 개수로 구분한다. 성능 JSON에 실제 응답 개수·요청 개수 일치·거부 사유·시작 충전/배터리/절전 상태를 추가했다.

사용자 요청에 따라 충전 여부와 관계없이 배터리 30% 이상·절전 꺼짐·열 상태 MODERATE 미만·메모리 여유·키보드 비활성일 때 자동 준비하도록 변경했다. 기존 명시적 켜기와 기본 꺼짐, 시도 예산, 입력 우선 중지를 유지한다. 정본은 [한국어 스마트 입력 SSOT](korean-smart-input-ssot.md)이며, 이전 충전 필수 조건의 성능 기록과 구분한다. 첫 기능 진입 화면에는 모델 준비 → 문장 미리 준비 → 입력할 때 바로 제안을 크게 안내하고 실제 대기 이유를 갱신한다. 정식 앱의 별도 온보딩 승격은 포함하지 않는다.

### 빌드와 테스트

`integrated-r1`은 WorkManager API 호출과 화면 괄호 오류로 컴파일 실패했다. 이때 남아 있던 XML·APK는 이번 변경의 검증 증거가 아니다. `integrated-r2`는 새 테스트가 정상 3어절 문장을 거부 대상으로 잘못 가정하여 1개 실패했다. 제품 코드의 허용 기준을 바꾸지 않고 실제 2어절 거부와 정상 3어절 수용을 함께 검증하도록 테스트를 수정했다.

`integrated-r3`은 JDK 17, 전체 단위 테스트·앱·AndroidTest 빌드가 56초에 성공했다. 실제 새 XML은 1,157개, 실패·오류 0개, 기존 스킵 7개, 통과 1,150개다. 배터리 정책 8개와 프롬프트 계약 4개를 포함한다. 앱 SHA-256은 `A3107F9DCE9EC14159382450375DAC792471B9394D2CBE94A528B67C9353B369`, 당시 테스트 APK는 `25B4F13EC077576534D2450BDD6C0A27364A11E77523D6CF6480B4E441692192`다. 이후 D 테스트에 실제 WorkManager 충전 제약 검사를 추가한 `device-test-r4`는 28초에 빌드 성공했으며 테스트 APK SHA-256은 `B72026F709F2C9981DDBFCA781AE8FA491A3827DA8BA98C14BE0708D766B07A5`다.

### 기기 검증 명령 오류와 복구

검증 워커의 PowerShell 함수가 자동 변수 `$args`를 매개변수로 사용하여 지정 클래스 옵션이 빠졌다. 그 결과 `missing-prefix8-after-r1`, `missing-prefix18-after-r1`, `coverage-after-prompt-r1`은 계획한 단일 검사가 아닌 전체 56개 검사를 호출했다. 세 로그는 의도한 검증 증거로 수용하지 않는다. 첫 중단 뒤 host 스크립트가 후속 명령을 실행한 사실도 확인했다. 현재 host에는 ADB 서버만 남아 있고 잘못된 instrumentation 프로세스가 없음을 직접 확인했다.

마지막 오실행이 자동 축적 검사를 시작한 상태에서 중단되어 `enabled=true`가 남았다. 오케스트레이터가 실제 화면 스위치로 원래의 꺼짐 상태를 복원했다(`recovery-ui-disabled.xml`). 이후 정확한 클래스·메서드만 지정한 `coverage-recovery-r3`은 `numtests=1`, 은행 53개, 공개 18/20문맥, `reloaded=true`, `generationActive=false`를 확인했다. 원래 43개에서 늘어난 10개는 계획한 새 공개 응답 품질 표본으로 사용하지 않는다. 시도 횟수는 초기화하지 않았고 은행을 삭제하지 않았다. 빈 문맥 8·18 때문에 이 coverage 검사 자체는 실패다.

이후 기기 명령은 옵션을 직접 명시한 단일 명령으로 실행하고 프로세스 종료까지 추적한다. 로그 요약의 JSON 파싱 실패를 정규식으로 보완하던 첫 helper도 반려했고, UTF-8 읽기와 실패 분리로 수정한 뒤 수용했다.

### 프롬프트 수정 후 저장·품질 관측

두 번째 프롬프트 빌드는 `prompt-r2-build-logged.log`에서 26초 성공, 계약 테스트 4개 통과다. 앱 SHA-256은 `C1E680EE2644A7E33C90BC45FDB093360E035BB684284E8F07C70C47F53015F9`, 테스트 APK는 `038DA4E4C75513633A1C7832DE7E23F8A2A6FE4F7ED52646383191234791677A`다. `prompt-r2-prefix8/18`은 4개 저장·0개 거부로 은행 57→61이다. `시간이 괜찮으면 같이 밥 먹을래?`는 일상 문장으로 자연스럽지만 프롬프트의 존댓말 지시는 지키지 않았다. 자연스러움과 지시 준수를 구분한다.

전체 공개 문맥의 새 응답 검사를 시작한 `fresh20-r2-batch0`은 문맥 0~3에서 요청당 정확히 2개, 총 8개 저장·0개 거부, 은행 61→69다. 추론은 요청당 6,737/6,781/6,927/7,354ms, 시작·종료 thermal 1, 충전 true, 배터리 100%였다. 8문장 모두 문맥상 사용할 수 있으나 `오늘 저녁`의 2문장은 반말이다. 다음 `fresh20-r2-batch4`는 내부 온도 검사에서 생성 전에 실패했다. 이후 배치는 실행하지 않았다. 이 검사는 전체 20문맥의 새 품질 평가 완료가 아니다.

### 사용자의 발열 허용 요청에 따른 정책 변경

사용자가 “좀 뜨거워도” 준비하기를 요청하여 MODERATE부터 중지하던 정책을 변경한다. [Android PowerManager](https://developer.android.com/reference/android/os/PowerManager)는 MODERATE를 사용성 영향이 크지 않은 제한, SEVERE를 사용성 영향이 큰 제한으로 구분한다. [Thermal API 안내](https://developer.android.com/games/optimize/adpf/thermal)는 열 여유가 줄 때 작업량을 낮추는 방식을 설명한다. 특정 온도나 모델의 무조건적인 안전성을 보장하는 근거로 사용하지 않는다.

공용 시작·감시·저장 가드는 SEVERE 이상에서 중지한다. MODERATE에서는 자동 작업의 실행당 예산을 4문맥에서 1문맥으로 줄이며, 해당 실행에서 식어도 예산을 다시 늘리지 않는다. 남은 문맥은 기존 15분 정기 예약에서 이어간다. 충전 불필수·배터리 30%·절전/키보드/메모리 조건과 시도 보존은 유지한다. 수동 생성에도 공용 가드를 적용했다. 이 절의 변경은 앞서 보존한 MODERATE 실패 기록을 통과로 바꾸는 것이 아니다. 새 빌드와 실제 기기 검증 결과는 별도로 기록한다.

`thermal-r3-build`는 전체 단위 테스트·앱·AndroidTest 빌드가 1분 12초에 성공했고 exit 0이다. 사본 XML 191개에서 총 1,160개·통과 1,153개·기존 스킵 7개·실패/오류 0개를 직접 확인했다. MODERATE 허용, SEVERE 차단, 4/1/0 예산과 예산 감소 후 회복 시 유지 검사를 포함한다. 앱 SHA-256은 `89715AEDE6C46055C49C272F880FCCD50106B126B03D543BB9567EED70BCAB42`, AndroidTest는 `2898B9FA1C8D32326175B15856E956C675498A749BF8F82CA9AAD50EE78BE51E`다. 최초 설치는 `thermal-r3-install.log`의 `device offline`, exit 1로 실패했으며 D/E를 호출하지 않았다. 연결 복구와 새 설치 후 검증이 필요하다.

연결 복구 조회에서도 기존 Fold6 주소는 offline이고 mDNS 발견 주소가 없었다. 기존 주소 `100.109.125.97:39155`의 연결 요청은 연결 거부(10061)로 실패했다. 현재 기기의 무선 디버깅 IP/포트 확인이 필요하다. 서버 강제 종료·기기 재부팅·페어링 변경은 하지 않았다. 새 발열 정책의 설치/실기기 통과로 보고하지 않는다.

남은 검증은 새 APK를 데이터 유지 설치한 뒤 실제 SEVERE 미만에서 D 자동 준비·끄기·재로드와 E 입력 중 native 중지를 확인하는 것이다. MODERATE에서도 한 번의 실제 생성이 가능해야 하며 상태를 조작하지 않는다. 이후 새 공개 품질 평가의 미실행 문맥 4~19를 확인하되 8·18의 별도 소표본과 구분하고, 표시·터치·띄어쓰기 검사 및 최종 자동 준비 false·은행 보존을 다시 확인한다. 충전하지 않는 실제 기기 조건과 장기 배터리 영향은 아직 측정하지 않았다. 오케스트레이터는 정책·UI 구현 diff와 전체 테스트 원문을 수용했으며, 기기 미실행을 완료로 바꾸지 않았다.

연속 goal 턴의 `continuation-connection-r2`에서도 기존 주소 연결은 10061로 거부됐다. Fold6가 연결 목록에 없고 mDNS에서도 새 주소를 발견하지 못해 설치와 생성 검증을 실행하지 않았다. 이는 동일 연결 차단의 두 번째 턴이며 목표는 미완료·활성 상태로 둔다. 기기 주소를 받기 전 구포트 반복 접속이나 모델 없는 에뮬레이터로 실기기 증거를 대체하지 않는다.

세 번째 연결 차단 턴에서도 오케스트레이터가 직접 실행한 `adb devices -l`에는 `emulator-5554`만 있고 `adb mdns services`는 비어 있었다(exit 0). 같은 기기 연결 부재가 세 턴 연속 확인되어 목표를 `blocked`로 기록한다. 완료 판정이 아니다. 코드·빌드·모델·은행·검증 로그는 보존하며, Fold6의 현재 무선 디버깅 연결 주소를 받으면 새 APK 설치와 위 남은 검증부터 재개한다.

### 새 연결 주소 수신 후 재개

사용자가 제공한 `100.109.125.97:36251`에 처음 연결하여 Fold6 `SM-F956N`, arm64-v8a, 배터리 52%, 충전하지 않음, thermal 0, override false를 확인했다. 이 값은 연결 직후 관측이며 이후 상태를 보장하지 않는다. 원문은 `.artifacts/gemma-resume-20260909/`에 보존했다.

최신 UI와 발열 정책을 포함한 arm64 앱·AndroidTest 빌드는 `arm-build.log`에서 1분 13초, exit 0으로 통과했다. 앱 SHA-256은 `E26B028DE689FAE1C4BD6B510A2131685B74D2B562E05E03E7E776034B88D559`, 테스트 APK는 `AFBDC95B3A60026AB6CE8A0E2A44BC8CDFA02B8505F1C907DF57172FECEE6C45`다.

설치 전 생성 없는 coverage 조회를 시작할 때 기기가 offline으로 바뀌어 계측은 실행되지 않았다. 검증 워커의 보고 명령에는 `fcitx5` 패키지 오타도 있어 실행 명령으로 수용하지 않는다. 오케스트레이터가 같은 주소로 다시 연결한 결과 연결 거부 10061과 offline을 확인했다. 앱·테스트 설치, 생성, 설정 변경은 수행하지 않았으며 기존 기기 데이터는 그대로다. 현재 무선 디버깅 연결 주소가 확인되면 정확한 클래스명을 사용하는 설치 전 조회→데이터 유지 설치→설치 후 조회부터 재개한다. 이번 새 주소 수신 후의 연결 차단 감사는 첫 턴으로 센다.
