# 공개 문맥 지속 확장과 온디바이스 우선 전환

## 범위와 결정

사용자는 고정 20문맥을 넘어 제한 없이 문맥을 넓혀 테스트하고, AI를 온디바이스로 옮기는 방향을 요청했다. 이 작업은 **디버그 Gemma 자동 준비에서 고정 문맥 목록과 목표 달성 종료를 제거**한다. 생성 대상의 시작 구절은 목록에 제한되지 않는다. 저장·배터리·발열 예산을 없애거나 모델을 상시 실행한다는 의미가 아니다. 정본 계약은 [한국어 스마트 입력 SSOT](korean-smart-input-ssot.md)의 공개 문맥 지속 확장 절이다.

공개 일상·업무 상황 12종과 발화 의도 6종을 순환하는 탐색 단서를 사용한다. 이것은 허용되는 문장 시작 구절 목록이 아니다. 첫 6요청부터 질문·요청·제안·상태 전달·확인·응답을 섞고, 72조합을 모두 순회한다. 다음 회차도 계속 진행한다. 최근 생성 문장의 시작 두 어절 최대 12개를 피하도록 요청한다. 중복이 실제로 제거됐는지는 저장 보고와 새 출력으로 확인해야 한다.

개인 입력·금고·클립보드·외부 화면은 프롬프트에 넣지 않는다. 최근 구절은 암호화된 **공개 생성 은행**에서만 가져와 기기 내부 모델에 전달하고 로그로 출력하지 않는다. 개인 문장 검색과 공개 생성 재료를 합치지 않는다.

## 유지하는 자원·보존 계약

- 기존 은행 v1, 2,000문장·1MiB 상한과 기존 보존 우선순위를 유지한다. 저장 포맷을 마이그레이션하거나 기존 문장을 지우지 않는다.
- 요청당 2문장, 실행당 최대 4요청·시작 예산 120초, MODERATE에서 1요청, SEVERE 중지, 배터리 30%·절전·메모리·입력 우선 조건을 유지한다.
- 신규 저장이 없는 요청이 6회 연속이면 정지한다. 사용자 다시 시도는 무성과 수를 초기화하되 공개 순번은 되돌리지 않는다.
- 공개 순번·무성과 수는 별도 상태 키다. 기존 prefix별 attempts·cursor·켜짐 상태를 삭제하지 않는다. 취소는 순번을 소비하지 않으며, 결과 저장을 마친 요청만 순번을 증가시킨다.
- 기존 20문맥과 prefix 전용 저장 API는 비교·회귀용으로 보존한다. 자동 준비의 완료 기준으로 사용하지 않는다.

## 온디바이스 전환 판단

핵심 입력은 온디바이스 우선으로 진행한다. 지금 Gemma 모델 경로는 재료 생성과 로컬 조회에 연결되어 있고, 모든 AI 기능을 대체한 상태가 아니다.

| 기능 | 현재 확인한 경계 | 후속 완료 조건 |
| --- | --- | --- |
| 입력 중 후보·오타·개인 문장 검색 | 로컬 인덱스·모델이 존재한다. 생성 재료도 이 경로로 조회한다. | 기존 목록 밖 실제 입력에서 표시·선택·삽입·유용성 검증 |
| Gemma 자동 문장 준비 | 로컬 모델 파일과 LiteRT-LM CPU 경로. 이번에 공개 문맥 지속 확장으로 변경 | 새 문맥 생성·재로드·조회·실제 터치 및 키보드 활성 시 취소 증거 |
| 글쓰기·말투·답장·번역 | 외부 Responses/컴패니언 경로가 남아 있다. `allowsAiInputFeatures`는 네트워크 정책에 의존한다. | 명시적 온디바이스 실행 계약, 한국어 품질·지연·취소·입력 세션 보존 검증 후 연결 |
| 음성 | 기기 받아쓰기와 외부 전사 공급자 경로가 별도로 존재한다. 기기 받아쓰기라는 이름만으로 완전 오프라인을 보장하지 않는다. | 실제 네트워크 차단 상태에서 인식·기기 지원·권한·오류 검증 |

Google의 [Gemma 4 모델 카드](https://ai.google.dev/gemma/docs/core/model_card_4)는 E2B의 텍스트·이미지·오디오 입력과 텍스트 출력, 음성 인식·음성 번역 기능을 설명한다. 이것은 현재 APK의 음성 구현이나 한국어 정확도 증거가 아니다. [LiteRT-LM Kotlin 문서](https://github.com/google-ai-edge/LiteRT-LM/blob/main/docs/api/kotlin/getting_started.md)는 엔진 초기화·수명 관리 API를 제공하지만 기기별 성능을 보증하지 않는다. 확인일은 2026-09-10이다.

외부 공급자 설정을 삭제하거나 로컬에서 실패했을 때 몰래 외부로 보내는 경로를 추가하지 않았다. 전체 온디바이스 전환은 아직 완료되지 않았다.

## 검증 상태

초기 focused 검사 57개 중 새 fixture 오류 1개를 정정했다. 한글 없음 검증에 `영문 시작 `이라는 한글 문자열을 쓴 오류였으며 제품의 검증 조건은 바꾸지 않았다. 정정 후 57개·실패 0·오류 0·스킵 0이다.

실제 생성·저장·입력 유용성과 통합 결과는 후속 검증 결과 절에 기록한다. 이 문서의 구현 설명만으로 품질·실기기 완료를 주장하지 않는다. 증거 폴더는 `outputs/gemma-open-contexts-20260910/`다.

## 후속 검증 결과

통합 단위 검사 수집 1,188개 중 1,181개 통과, 기존 스킵 7개, 실패·오류 0개다. 앱 빌드가 통과했고, instrumentation 소스의 누락된 `Build` import를 복구한 뒤 테스트 APK도 빌드에 성공했다. 기존 데이터 유지 설치 후 읽기 전용 검사에서 125문장, 재로드 성공, 생성 비활성을 확인했다.

Fold6(SM-F956N), CPU에서 명시적 6요청을 실행했다. `open-generation.log`의 `OK (1 test)`와 요청 인덱스 0~5를 확인했다. 각 요청이 2문장씩 추가돼 저장량은 125→137개다. 중복·거부는 모두 0개였고 자동 준비 순번은 수동 실험 전후 0으로 보존됐다. 순수 생성 시간은 요청당 8.238~8.682초, 준비·저장을 포함한 시간은 12.960~15.510초다. 이 시간은 입력 중 후보 조회 지연과 구분한다.

새 출력에는 `내일 시간 괜찮으세요?`, `이 버스는 몇 시에 도착해요?`, `오늘 저녁 같이 식사할래요?`, `구매한 물건이 도착했는지 알려주세요.` 등이 포함됐다. 12문장의 문법·의미 연결에 뚜렷한 오류는 확인하지 못했지만, 질문·제안·요청에 치우쳤다. 프롬프트가 상태 전달·응답을 지정해도 그 의도를 충분히 따르지 않는다. 따라서 상황 확장과 저장 성공은 확인했으나 발화 의도 다양성이나 일반 입력 정확도 개선이 입증된 것은 아니다.

후속 품질 과제는 의도별 준수율과 실제 입력에서 새 후보가 유용한 비율을 별도 평가하는 것이다. 생성량만 늘리는 것을 정확도 개선으로 계산하지 않는다. 2,000문장 상한 이후의 장기 교체·다양성 유지도 이번 6요청으로 검증하지 않았다.

새 공개 문장 `내일 시간 괜찮으세요?`의 접두부를 Base64 인자로 전달한 실제 키보드 검사는 `latency.log`에서 `OK (1 test)`다. 후보 데이터 준비 30ms, 화면 표시 422ms, 실제 touch down/up 주입과 정확한 삽입 모두 성공했다. 기존 고정 목록 밖의 새 문장을 입력 경로로 연결한 1사례 증거이며, 일반 입력 전체의 적중률 측정은 아니다.

백그라운드 자동 준비는 thermal status 2에서 실행되어 137→139문장, 공개 순번 0→1로 진행했다. `accumulate-background.log`에서 `addedOpenContext=true`, `pausedNoNative=true`, `reloaded=true`, `stable=true`, `OK (1 test)`를 확인했다. 이 실행의 신규 저장은 2개다. `stateAdded=62`는 기존 누적 메타데이터이며 이번 실행 생성량으로 사용하지 않는다.

키보드 중단 검사도 thermal status 2에서 `OK (1 test)`다. 활성 native 생성을 먼저 관측한 뒤 실제 키보드 활성으로 생성이 중단됐고, 139문장·공개 순번 1·무성과 수 0이 안정적으로 유지됐다. 취소가 순번을 소비하지 않는 실기기 증거다. 최종 읽기 검사도 통과했고 139문장·재로드 성공·생성 비활성, 설정 `enabled=false`를 확인했다. 각 후속 검사는 재시도 없이 1회 실행했다.

구현 워커의 변경과 검증 워커의 원문을 오케스트레이터가 검토해 수용했다. 잘못된 테스트 fixture와 누락된 import는 수정 후 재검증했다. 별도 `accumulateNewPublicContexts` instrumentation은 컴파일만 확인했으며, 실제 자동 준비 경로는 위 백그라운드·키보드 검사로 검증했다. 자동 준비를 계속 켜 둔 장시간 누적과 일반 입력 적중률 평가는 미완료다.
